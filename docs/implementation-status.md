# Implementation status against the supplied plan

This records what the current repository proves. The [implementation plan](implementation-plan.md) remains the release target. Its Tier 1 section specifies a seeded, replayable in-memory transport model, differential contract checks against real NATS, and incremental proof gates. The seeded and differential results below cover several transport slices, including short worker execution, signal resume, native timer wakeup, and fallback timer scan-to-worker wakeup; other integrated paths remain unfinished.

## Configuration deviations verified against NATS

- JetStream atomic batches commit inside one stream, so `WF_INV` and `WF_RUN` cannot be started in one batch. The start reconciler repairs the gap.
- Scheduled messages and their targets must be in one stream. The server rejects schedules with `DiscardNew`, so `WF_RUN` uses `DiscardOld` with unlimited messages, bytes, and age. Provisioning rejects limits that could silently evict live work.
- Per-message TTL deletes an unread message at expiry. The fallback keeps a `WF_TIMER` record without TTL and deletes it only after a due `WF_RUN` publish is acknowledged; TTL expiry cannot safely serve as the poller trigger. The fallback passed with scheduling disabled on the current three-node fixture and with an opt-in NATS 2.11.17 server binary.
- `EnsureAuto` preserves the existing `WF_RUN` scheduling mode. On an empty deployment it selects by the connected server version and fails closed when that version is unavailable; it does not prove that all peers in a mixed-version cluster support scheduling.
- Retention purges `WF_TIMER` subjects for the retiring invocation sequence after its journal and before its tombstone. A crash injected after that stage resumes correctly, and records for other generations remain untouched.
- The fallback poller also removes records proven retired by a matching purge marker or tombstone. Workers renew their lease before timer publication; an extreme pause between renewal and publication can still leave a late record, which the poller removes while the retirement marker remains available.
- Lease creation revisions serve as epochs. They remain unique even when a lease expires before its first journal append.
- Scheduled timer publish IDs include the invocation sequence as well as the logical step, so a reused ID cannot deduplicate a new generation's schedule against an old one.
- Journal snapshots use a separate `snap.<type>.<id>` manifest in `WF_STATE` and a hashed object in `WF_BLOB`. Reads reconstruct the logical journal from the object and newer live entries. Compaction currently retains the newest 16 entries and purges with a fixed stream sequence bound, so later appends survive. The full-prefix object is rewritten at each snapshot; this is correct but costly for long journals.
- The long compaction test exposed brief read-after-write lag across replicas: an acknowledged snapshot object or KV manifest was sometimes invisible from a pinned node immediately afterward. Snapshot upload verification and bounded manifest/object read retries now precede purge. Persistent absence or hash mismatch still fails closed with `ErrGap`.
- Retention tombstones carry an expiry time that `client.Await` honors. `retention.SweepTombstones` removes expired KV entries once the old invocation is gone, with a revision precondition that protects concurrent replacement. The CLI exposes a one-shot sweep; deployments must schedule it. `retention.SweepBlobsQuiescent` can reclaim unreferenced Object Store data after clients and workers stop; online reclamation needs a coordination protocol because Object Store deletion does not compare metadata revisions.
- Projection rebuild uses retained `WF_INV` records and `journal.Read` (including snapshot objects), because compaction removes the original `WF_JRN` prefix. Its consumer lag counts unacknowledged journal messages; it does not include invocation-only starts or purges, which the periodic rebuild detects.
